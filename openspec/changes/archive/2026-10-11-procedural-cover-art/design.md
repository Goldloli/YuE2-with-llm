# Design: procedural-cover-art

## 视觉配方（demo `compare/cover-options.png` C 行已验证）

| 层 | 参数 | 说明 |
|---|---|---|
| 基底 | 种子化色相 h，`hsl(h 30% 9%) → hsl(h+40 26% 14%)` 对角渐变 | 深色打底，避免过亮 |
| 流场笔触 | ~420 条，每条 14–40 步；方向场 `sin(x·0.018)+cos(y·0.021)+随机扰动`；线宽 0.6–2.8px（按画布比例）；透明度 0.05–0.14 | 主体纹理，缩略图仍可辨 |
| 强调色 | 3 色：`hsl(h+i·44+jitter, 58–80%, 44–60%)` | 与基底同色系，无刺眼撞色 |
| 暗角 | 径向 `transparent → rgba(0,0,0,0.5)`（0.32R 起渐深） | 聚焦中心、压暗四角 |
| 颗粒 | ImageData 逐像素 ±8（0–255 域） | 胶片质感，消除渐变条带 |

- 画布 256×256；显示尺寸全部 `background-size: cover` 缩放（46/84/240px 三档）。
- 种子：`hashCode(id)` → `mulberry32`；同 id 跨会话、跨位置、跨刷新严格一致。

## 关键决策

### 决策 1：函数契约不变，接入零侵入

`coverStyle(id)` 现有四处调用（`app.js:214` 列表行、`:242` 库网格、`:364` 详情面板、`:851` 播放条）全部以 `style="${coverStyle(...)}"` 或 `style.cssText` 消费样式串。新实现保持「传入 id、返回 CSS 样式串」契约，调用点零改动，可测试性与回滚面最小。

### 决策 2：内存缓存 + dataURL，而非每元素一个 canvas

每行一个 `<canvas>` 会在 DOM 增删（列表轮询每数秒重渲）中反复创建；dataURL 缓存让重渲只命中 `Map`。dataURL 生成一次（毫秒级）后无额外开销。缓存不设上限（歌曲量级为百，单张 ~30–80KB dataURL，内存可控）。

### 决策 3：懒生成 + 现有渐变回退

- 首次 `coverStyle(id)` 时同步生成（约 2–6ms），无预生成阶段、无异步闪烁；
- `canvas.getContext("2d")` 不可用或抛错时，回退现有双色渐变（保留原实现为 `fallbackGradient(id)`），保证任何环境下有可见封面。

### 决策 4：画布 256px 统一尺寸

详情面板显示 240px、行 84px、播放条 46px。统一 256px 导出，小尺寸端靠缩放获得天然抗锯齿；避免按显示尺寸多次生成（缓存键只需 id）。

### 决策 5：色相域限制在深色调域

基底固定 9%/14% 低亮度；强调色亮度 44–60%、饱和度 58–80%。demo 中验证无高饱和刺眼色。若实测个别 id 观感不佳，调参点集中在配方常量区（不在本提案范围外扩散）。

## 风险与缓解

- **首屏批量生成**：一次刷新最多生成 N 张（新增 id 数量级；实测单张毫秒级，50 首 <300ms 摊布在渲染中）。极端情况（数百新歌同屏）可后续加 `requestIdleCallback` 分批——当前不做，留作已知边界。
- **确定性回归**：`hashCode`/`mulberry32` 一旦改动，全部封面重排——两函数视为契约，改动需新提案。
- **基线全量重截**：封面全局可见，五张基线全部受影响；重截后对照确认除封面外零意外差异。
