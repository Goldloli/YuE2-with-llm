# Design: freeze-web-ui-design

## Context

`web/static/` 共 4 个核心文件：`index.html`（275 行，三栏 + 播放条骨架）、`styles.css`（629 行，设计令牌集中在 `:root`）、`app.js`（1566 行）、`i18n.js`（611 行，en/zh）。CSS 首行自述为暗色三栏音乐工作台视觉。令牌化程度已经很高（颜色/圆角/字体全部走 CSS 变量），这是「冻结」可行性高的关键前提。仓库已有 `compare/` 目录存放人工对比截图、`ref-suno/` 存放 Suno 参考截图，说明截图对照是该项目的既有工作方式。

## Goals / Non-Goals

**Goals:**

- 把当前风格写成可校验的能力规格（冻结契约），归档后常驻 `openspec/specs/web-ui-design/`。
- 建立两道保障：AGENTS.md 规则（约束 AI 助手）+ 提案显式声明机制（约束变更流程）。
- 提供基线截图作为人工核查参照。

**Non-Goals:**

- 不改动 `web/static/` 任何代码与样式。
- 不引入自动化像素回归框架（如 Percy/Playwright 快照断言）——动态内容（进度条、时间、列表数据）使像素级硬门禁脆弱且维护成本高。
- 不冻结交互行为与功能逻辑——冻结的是视觉风格，不是功能演进。

## Decisions

### D1: 用 OpenSpec 能力规格承载冻结契约

规格是本项目唯一被流程强制对照的产物（每个提案都要列 Capabilities、validate 校验 delta）。把设计基线写成 `web-ui-design` 能力的 ADDED 需求，归档后成为常驻 spec，后续提案修改它即构成显式的「视觉变更」信号——冻结因此嵌入既有流程而非依赖口头约定。

备选：只写进 AGENTS.md——AGENTS.md 无校验、无场景化验收标准，约束粒度太粗，否决（但仍作为 D2 的辅助层保留）。

### D2: AGENTS.md 增加冻结规则作为 AI 层保障

AI 助手每次会话读 AGENTS.md，规则写为「触及 `web/static/` 的提案必须自查 `openspec/specs/web-ui-design`；视觉变更必须显式声明并经用户确认」。这是规格之外对执行者的直接提示，成本一行字，收益是防止 agent 在未走提案的情况下顺手改样式。

### D3: 规格 pin 令牌值与结构，不复制全部 CSS 细节

spec 只固化「契约层」：令牌值、三栏尺寸、组件模式清单、动效上限。组件的内部像素细节（padding、字号阶梯）以代码为事实源，不进 spec——否则规格随实现细节腐烂，且超出「行为契约」的定位。

### D4: 基线截图定位为人工参照，非自动化门禁

用 Playwright（项目已有 `.playwright-mcp/` 与 webapp-testing 工作流）以固定视口 1440×900 截取 en/zh 两套关键页面，存 `docs/ui-baseline/`。规格用语 SHOULD（人工核查）而非 MUST（自动断言），因为歌曲列表、时间戳、进度等动态内容使像素级自动对比必然 flaky。

备选：不存截图——用户已有 `compare/` 人工对比习惯，缺的是一套「官方基线」，故保留。

### D5: 明确放行清单，避免冻结过度

纯文案/i18n、占位符、不可见行为修复、后端逻辑不算视觉变更，无需声明。这条写进 spec（视觉变更管控需求的场景），防止冻结机制演变成所有前端改动都要特批的官僚流程。

## Risks / Trade-offs

- [冻结导致合理的设计演进受阻] → 冻结的是「默认状态」，显式声明 + 用户确认即可合法变更，机制本身留有出口。
- [基线截图随功能新增而过时] → 截图定位为参照而非门禁；新增页面时按同一视口规范补截即可，规格不强制更新旧图。
- [spec 与现实 CSS 漂移（有人直接改令牌不走流程）] → AGENTS.md 规则 + 提案流程约束了 AI 助手路径；人工直接改代码属于流程外行为，spec 至少在评审时提供对照依据。

## Migration Plan

纯契约与文档变更，无代码迁移。落地顺序：提案确认 → 实施（AGENTS.md 规则 + 基线截图）→ archive 使 spec 生效。回滚即删除 spec 与规则，无副作用。

## Open Questions

- 基线截图是否纳入 `compare/` 现有命名体系还是独立 `docs/ui-baseline/`——倾向后者（语义清晰），实施时可定，不影响规格与任务。
