# Design: model-manager

## 关键决策

### 决策 1：下载数据面改用 curl 子进程（性能修复，实测驱动）

实施中发现 `tools/hf_download.py` 的 urllib 数据面被 hf-mirror 稳定限速到 **~0.9 MiB/s**（curl 同 URL 3–11 MiB/s；UA 无关、HTTP/1.1 与 h2 无关、302 后直连 huggingface.co 文件路径同样慢）——大模型下载（3.4–7 GB）在该速率下不可用。改造：**所有数据传输改用 `curl -sSL --fail --retry` 子进程**（macOS/Linux 自带；Windows 10+ 自带 `curl.exe`），保留原有的分块并行架构与完整性校验；`head_size` 保留 urllib（单次请求，速度无关）。实测：同一下载从 0.9 MiB/s 提升至 **14–19 MiB/s**。

### 决策 2：修复下载器 416 与失败态两个 bug（实测暴露）

1. `download_small` 对已完整的小文件仍发 Range 续传请求 → 服务端 416 → 整个下载任务退出。修复：先以 HEAD 大小判定完成态（skip），部分文件下载前清空重下（小文件代价可忽略）；
2. 管理器把「进程已死的失败任务」仍标记为下载中。修复：`snapshot()` 增加 `running` 标志（进程存活判定），payload 仅在 `running` 时置 `downloading`；失败条目保留错误文本直至下一次发起（`start` 会清除死条目允许重试）。

### 决策 3：下载通道与主任务队列并行

下载是纯 IO 子进程，不占 GPU，与生成/转录的主队列（单 worker）**并行**运行（独立线程 + 单并发下载通道）；实测：mlx-4bit 下载进行中，一首 10 秒歌正常生成完成，互不阻塞。同组件或异组件在下载中再次发起均返回 409（单通道）。

### 决策 4：进度的磁盘字节口径

进度 = 组件目标路径当前落盘字节（含 `<file>.parts` 分块）÷ 组件标称体积。不解析下载进程输出（`hf_download.py` 无百分比输出），字节轮询对 3–7 GB 级下载足够精确（秒级更新）；取消后保留分块，重发即续传（实测 16%→取消→重发→17% 继续）。

## 与既有机制的边界

- `bootstrap.py` 首启流程不变（CLI 用户仍可整组安装）；模型页是运行后的细粒度管理入口，两者共用 `hf_download.py` 的模式。
- 删除模型不在范围（Non-goal）：需要释放空间时依然走文件系统。
- MLX 组仅 darwin 显示（`platform` 字段过滤，服务端与前端双层）。
